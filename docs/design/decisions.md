## 1. 已确认

| 议题 | 用户决定 | 对设计的约束 |
| --- | --- | --- |
| Q1 范围 | 整体重构 | 覆盖完整产品体验，首页、执行、回看和管理统一设计 |

| Q10 足迹 | 统计优先 | 摘要与分析位于记录列表之前 |
| Q11 目标选择 | 可直接在首页用弹窗选择 | 入口从首页可达，不只放在设置或详情页 |
| Q12 视觉 | 不用沿用上传参考或当前项目，重新设计 | 全新探索布局、颜色、排版与容器 |
| Q13 产品问题 | AI 已拆小任务，需要工具计时与跟踪 | 产品承接执行，不追加拆解或激励流程作为开始条件 |
| Q14 AI 边界 | 外部 MCP 已跑通；内部 AI 后续考虑 | 当前设计围绕外部 AI 写入与 Web 执行 |

| 补充：主导航 | 改为左侧侧边栏，替代顶部 Tab | 两个界面方向均采用左侧导航；目标选择仍从首页弹窗进入 |
| 补充：Onboarding | 首次打开应用的体验需要优化 | 将已有计划、AI 写入与手动创建的首次执行衔接纳入整体 redesign |

Q11 没有要求取消详情管理页；首页弹窗承接选择。Q12 否定暖白橙色作为指定方向，不能把历史截图作为最终风格批准。

侧边栏的专注时折叠、移动端抽屉是设计建议，用户尚未逐项确认。足迹中的日／周／月／年仍为内容区周期选择，不是全局主导航。

首次打开的新流程见 [Onboarding 提案](onboarding.md)。AI 接入为主入口、单屏手动创建与默认基础设置均是建议，尚未把它们记为用户已确认决策。

## 3. 需要最终澄清的领域边界

用户确认了四轮有四条独立记录，但上一轮提问包含两个不同问题：记录如何展示，以及计时过程何时结束。后者没有被“四条展示”自动回答。

现有词汇表定义一条 Session 可以包含多轮。可以保留一个多轮 Session，把每个 Focus Round 作为独立的足迹条目；也可以让一轮对应一条 Session。两者对执行次数、取消范围、笔记／接续提示归属和 MCP 契约有不同影响。

最终问题：**多轮过程是否继续保留“设定轮数后自动结束”的生命周期，每轮独立记账；还是每轮到时就结束一次 Session，下一轮属于新 Session？**

推荐保留多轮过程、每轮独立展示，以符合用户“有四轮，每轮都有记录”的描述，并保留既有结束体验。此处为推荐，不作为已确认的数据重构决定。

## 4. 旧规范与实现需要同步的位置

这里只登记差异，不让旧页面约束新设计，也不提前修改正式 PRD。

| 现有依据 | 事实／差异 | 后续处理 |
| --- | --- | --- |
| `docs/prd.md` §5.1 | 规定准备首页计时器居中 | 选定新方案后改为当前工作优先，区分准备与专注状态 |
| `docs/prd.md` §5.1、§5.3 | 对其他页计时入口与离开限制有相互矛盾描述 | 以用户 Q4 为准，保留离开限制，删除另一套叙述 |
| `docs/prd.md` §6.3–6.4 | 默认每四轮长休息 | 用户已否定长休息；短休息仍由用户主动开始 |
| `src/components/today/run-panel.tsx` | 当前达到配置轮数会自动结束整个 Session | 澄清整次生命周期后同步 PRD 与 Web／MCP 行为 |
| `CONTEXT.md` Session 与 `docs/prd.md` §7.1 | 多轮 Session 在主历史只展示一次 | 新足迹要求每轮独立展示；记录映射和计数口径需明确 |
| `src/services/dashboard.ts` | 运行时不提供接续提示；今日摘要不含目标累计与提示来源时间 | 按新页面实际需要调整读模型，运行恢复不能只依赖启动时的客户端缓存 |
| `src/services/statistics.ts` | 已有按目标及按日聚合；周期有 today/week/month/custom/all，没有原生 year 选项 | 增加明确的年份浏览体验，评估自然年范围与月聚合；不把已有 custom 能力等同于完整年分析 UI |
| `src/components/session-navigation.tsx` | 已有结束并保存后离开的确认 | 用户确认沿用，不重新引入跨页面计时 |

每轮展示独立不等于对当前数据作四份复制。后续设计必须防止 Focus Interval、Focus Round 与 Session 汇总重复计时。

## 5. 术语与文档维护

根目录 `CONTEXT.md` 仍是领域词汇的唯一来源。本轮只补充 Focus Round，用于区分一个番茄专注阶段和暂停拆开的多个实际专注区间。

首页、选择弹窗和专注场景属于界面结构，不新建领域对象。配色与布局容易调整，当前不为它们创建 ADR。每轮身份与统计口径待最终确认；如最终改变领域身份或 MCP 契约，再记录对应的领域决策。
