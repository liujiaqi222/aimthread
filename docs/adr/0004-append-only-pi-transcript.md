# 回合 transcript 按 pi 原格式只追加存储，协议合法性只在构建上下文时统一保证

AI 回合（Turn）的 transcript 按 pi 的 `Message` JSON 原样逐条存储，带 pi 版本与格式版本，不转成自有格式。transcript 只追加、不改写：卡片（Card）提出时写入占位 toolResult 并结束回合；用户之后的决定先写在卡片业务表，在下一次回合开始时合成一条事实消息，先落库再发给模型。system 提示词和当前目标事实每回合重新组装，不写进 transcript；动态事实放在请求末尾，保证历史前缀在回合之间只增不改，prompt cache 能持续命中。

中止、崩溃、服务商报错会留下不完整的回合。落库时只做两件事：参数没生成完的 tool_use 不落库；建卡片行和写它的占位 toolResult 在同一个事务里完成。发给模型的消息序列是否合法（每个 tool_use 都有配对的 result、末尾不是 assistant 消息），只由构建上下文的一个函数统一保证：所有非 completed 的回合都裁剪到最后一个协议完整的位置。被裁掉的内容仍留在库里供界面展示。

决定来源：[pi 适配边界与 AI 回合持久化](https://github.com/liujiaqi222/aimthread/issues/54)。

## Considered Options

- **转成自有消息格式**：不受 pi 升级影响，但会丢失 `thinkingSignature`、服务商戳记等字段，每次重建都要转换两次，容易出错。pi 已锁定版本，升级时有 faux 回归测试兜底，必要时写一次数据迁移，代价更小。
- **按卡片当前状态改写 toolResult**：模型直接看到最新决定，但历史会随卡片状态变化，难调试，每次决定都会让 prompt cache 失效。
- **在落库时把 transcript 净化成始终合法**：读取简单，但中止、崩溃、报错各需一套净化规则，容易遗漏；而且崩溃时来不及净化。统一放到构建上下文这一处，规则只有一份。
- **把目标事实放在 system 提示词末尾**：静态部分仍能命中缓存，但事实一变，后面的整段历史都会失去缓存。

## Consequences

- 升级 pi 时，如果 `Message` 格式变化，要为已存的 transcript 写迁移；锁定确切版本，faux 回归测试先通过才能升级。
- 卡片业务状态（待处理 / 接受 / 拒绝 / 过期）以卡片表为准，不从 transcript 解析。
- 构建上下文的合法化函数是 AI 模块中最需要测试的地方：中止、崩溃、报错、并行 tool call 部分执行都要覆盖。
- 切换角色会改变工具列表，这次请求无法命中缓存；这一点可以接受。
